# handlers/

## Overview

The handlers directory contains IPC (Inter-Process Communication) handler modules that form the secure bridge between Electron's main process and renderer process. These handlers expose main process functionality (file system operations, Git integration, shell access, etc.) to the renderer process through typed, secure IPC channels.

## Architecture

### IPC Communication Pattern

All handlers follow a consistent pattern:
1. Renderer process makes requests via `window.api` methods defined in `preload.ts`
2. Handlers in main process receive requests through `ipcMain.handle()` or `ipcMain.on()`
3. Handlers delegate to appropriate service classes (FileService, GitService, etc.)
4. Results are returned to renderer or errors are properly propagated

### Security Model

- All file system operations go through FileService abstraction
- Path normalization and validation happens in main process
- No direct file system access from renderer process
- API keys and sensitive data handled only in main process

## Components

### contextHandlers.ts

**Purpose**: Provides intelligent context calculation for AI prompts.

**Key Features**:
- Calculates relevant files based on selected files and task description
- Integrates with RelevanceEngineService for heuristic analysis
- Respects token limits from application settings
- Returns structured context with user-selected and heuristically-discovered files

**Dependencies**:
- RelevanceEngineService: For relevance calculations
- SettingsService: For token limit configuration

### coreHandlers.ts

**Purpose**: Core IPC handlers for essential application functionality.

**Key Features**:
- File system operations (exists, isDirectory, path utilities)
- Dialog operations (confirmations, folder selection)
- Application metadata (version, user data path)
- Project management (opening folders, setting base directory)
- Ignore file management (.athignore operations)
- Platform-specific path conversions
- External link/path opening with security checks

**Notable Implementation Details**:
- Special handling for Linux `xdg-open` requirement
- CLI path support for opening projects from command line
- Validation for project info files within project directory

**Dependencies**:
- FileService: All file operations
- SettingsService: Application/project settings
- Electron APIs: dialog, app, nativeTheme, shell

### coreHandlers.test.ts

**Purpose**: Comprehensive test coverage for coreHandlers.

**Testing Approach**:
- Full mocking of Electron APIs and services
- Tests all 23 IPC channels
- Covers success paths and error conditions
- Special cases for null mainWindow, destroyed webContents
- Platform-specific behavior testing

**Test Organization**:
- Handler registration tests
- Individual handler test suites
- Edge case coverage (permissions, missing files, etc.)

### fileOperationHandlers.ts

**Purpose**: File and directory operation handlers.

**Key Features**:
- File reading/writing with encoding support
- Directory listing with ignore rule application
- File deletion and directory creation
- Template path resolution
- Automatic path normalization and relativization

**Path Handling Strategy**:
- Converts all paths to Unix format internally
- Relativizes absolute paths within project directory
- Preserves absolute paths outside project directory
- Supports both string and object encoding options

**Dependencies**:
- FileService: All file operations
- PathUtils: Path validation and manipulation

### fileWatchHandlers.ts

**Purpose**: Real-time file system monitoring.

**Key Features**:
- Directory watching with change notifications
- Automatic cleanup of existing watchers
- Event forwarding to renderer process
- Proper resource cleanup on watcher removal

**Implementation Details**:
- Maintains map of active watchers by path
- Checks for destroyed senders before event emission
- Supports batch watcher cleanup

**Dependencies**:
- FileService: Watcher implementation
- PathUtils: Path handling

### gitHandlers.ts

**Purpose**: Git repository operations.

**Key Features**:
- View uncommitted changes with diffs
- Get file content at HEAD revision
- Check if current directory is Git repository
- Structured diff data with old/new content

**Error Handling**:
- Graceful handling of deleted files
- Warnings for read failures during diff generation

**Dependencies**:
- GitService: Git operations
- FileService: Current file content reading

### llmIpc.ts

**Purpose**: LLM (Language Model) integration handlers.

**Key Features**:
- Get available providers and models
- Send messages to LLM providers
- Check API key availability (storage or environment)
- Support for multiple LLM providers via genai-lite

**API Key Resolution**:
- First checks secure storage
- Falls back to environment variables (ATHANOR_*_API_KEY)
- Returns availability status without exposing keys

**Dependencies**:
- LLMService: Provider communication
- ApiKeyServiceMain: Secure key storage

### settingsHandlers.ts

**Purpose**: Settings persistence and retrieval.

**Key Features**:
- Project-specific settings management
- Application-wide settings management
- Error handling with fallback to null
- Typed settings interfaces

**Settings Types**:
- ProjectSettings: Per-project configuration
- ApplicationSettings: Global app configuration

**Dependencies**:
- SettingsService: Settings persistence

### shellHandlers.ts

**Purpose**: Terminal emulation and shell session management.

**Key Features**:
- Check shell availability
- Start new shell sessions with PTY
- Attach/detach from sessions
- Write data to shells
- Resize terminal dimensions
- Kill shell sessions
- Test shell functionality

**Session Management**:
- Unique session IDs for multi-terminal support
- Persistent sessions across UI switches
- Platform-specific shell detection

**Dependencies**:
- ShellService: PTY and session management

## Error Handling

All handlers follow consistent error handling:
1. Try-catch blocks around operations
2. Error logging with context
3. Error propagation to renderer
4. Graceful fallbacks where appropriate

## Security Considerations

1. **Path Validation**: All paths validated in main process
2. **No Direct Access**: Renderer never accesses file system directly
3. **Secure Storage**: API keys handled only in main process
4. **URL Validation**: External URLs must be HTTP(S)
5. **Permission Checks**: File access permissions verified

## Best Practices

1. Always use FileService for file operations
2. Normalize paths to Unix format internally
3. Handle destroyed IPC senders gracefully
4. Provide meaningful error messages
5. Test both success and failure paths
6. Document security implications
