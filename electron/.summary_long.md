# Directory: electron

## Overview

The `electron/` directory contains the entire main process implementation for Athanor, providing the secure backend for all system operations. This directory implements the core intelligence, file system management, Git integration, and native OS capabilities that power the application. Following Electron's security best practices, it strictly separates privileged operations from the renderer process, exposing only safe, validated APIs through IPC.

The architecture demonstrates sophisticated patterns including service-oriented design, event-driven communication, background worker threads, and intelligent project analysis with minimal user disruption.

## Key Components

### main.ts

The application's entry point and orchestrator that coordinates all services and application lifecycle:

**Core Responsibilities:**
- Initializes all singleton services (FileService, GitService, ProjectGraphService, etc.)
- Manages application lifecycle and window creation
- Implements intelligent project analysis scheduling with debouncing
- Handles command-line arguments for direct project opening
- Sets up IPC communication bridges and menu system
- Coordinates background worker threads for CPU-intensive tasks

**Key Features:**
- **Two-phase analysis scheduling**: Waits for file system quiescence then user inactivity
- **Window focus awareness**: Prevents analysis during active work
- **Service initialization**: All services created as singletons on startup
- **Dynamic menu management**: Menu building with recent projects support
- **Window state persistence**: Saves and restores window position/size/maximized state
- **WSL graphics fix**: Environment variable support for graphics compatibility
- **CLI path handling**: Opens projects from command line arguments

**Notable Patterns:**
- Event-driven architecture with service event emitters
- Worker thread management for background analysis
- Graceful shutdown handling with proper cleanup
- Platform-specific fixes (WSL graphics, macOS dock)
- Automatic Git service base directory updates on project change

**Dependencies**: electron, worker_threads, fix-path, all service modules

### ignoreRulesManager.ts

Implements a sophisticated hierarchical ignore system for file filtering:

**Core Algorithm - "Deepest Opinion Wins":**
- Discovers all .athignore and .gitignore files in project
- Compiles rules into unified, pre-computed ruleset
- Implements "Athanor-First" precedence (athignore overrides gitignore)
- Uses discovered rules to prune directory scanning

**Two-Phase Processing:**
1. **Discovery Phase**: Recursively finds all ignore files
2. **Compilation Phase**: Transforms and merges rules for fast lookup

**Performance Optimizations:**
- Directory pruning during scan based on parent rules
- Pre-compiled ruleset for O(1) ignore checks
- Debounced loading (500ms) to prevent excessive rescanning
- Materials directory (.ath_materials) auto-exclusion
- Caches compiled rules until next reload

**Key Methods:**
- `loadIgnoreRules()`: Discovers and compiles all ignore files
- `ignores(path)`: Fast lookup using pre-compiled rules
- `addIgnorePattern()`: Programmatically adds patterns to .athignore
- `_scanForIgnoreFiles()`: Recursive scanner with intelligent pruning
- `_transformPatterns()`: Converts nested patterns to root-relative

**Pattern Transformation:**
- Leading slash patterns anchored to containing directory
- Simple patterns expanded with globstar for nested matching
- Negation patterns properly preserved and transformed
- Relative patterns made absolute from ignore file location

**Dependencies**: fs/promises, ignore library, PathUtils

### workers/projectAnalysisWorker.ts

Background worker thread for CPU-intensive project analysis:

**Purpose**: Runs project dependency analysis in separate thread to prevent UI blocking

**Process Flow:**
1. Receives baseDir from main process via workerData
2. Creates isolated service instances (FileService, GitService, ProjectGraphService)
3. Runs full project analysis including dependency scanning
4. Sends compiled graph data back to main thread
5. Main thread updates ProjectGraphService cache and notifies UI

**Communication Protocol:**
- Input: `{ baseDir: string }` via workerData
- Output: `{ success: boolean, data?: ProjectGraphCache, error?: string }` via postMessage
- Error handling with serializable error messages

**Key Features:**
- Complete isolation from main thread
- Independent service instances
- Graceful error handling and reporting
- Structured message passing

**Dependencies**: worker_threads, FileService, ProjectGraphService, GitService

## Data Flow

### File Operations Flow
1. Renderer calls window.fileService method
2. Preload forwards via IPC
3. Handler validates and delegates to FileService
4. FileService performs operation
5. Result returned through IPC chain

### Project Analysis Flow
1. File changes detected by watcher
2. Analysis scheduled after quiescence
3. Worker thread spawned
4. Multiple analysis phases executed
5. Results cached and UI notified

### Context Calculation Flow
1. User selects files and enters task
2. UI requests context calculation
3. RelevanceEngineService runs heuristics
4. ProjectGraphService provides relationships
5. Scored results returned within token budget
