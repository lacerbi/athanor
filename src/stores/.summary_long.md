# Directory: src/stores

## Overview

The stores directory contains Zustand-based state management for the entire Athanor application. These stores provide a centralized, type-safe way to manage application state with excellent performance and developer experience. The architecture demonstrates clean separation of concerns with each store handling a specific domain while maintaining integration points through shared types and IPC communication.

## Key Components

### workbenchStore.ts

The central workspace management store handling multi-tab functionality:
- **State Structure**: Array of TaskTab objects with id, name, content, output, context, and selectedFiles
- **Tab Management**: Create, remove, and switch between task tabs with smart numbering
- **File Selection**: Per-tab file selection with folder expansion and descendant handling
- **Prompt Generation**: Manages generation state with 30-second timeout protection
- **Key Features**:
  - File selection inheritance when creating new tabs
  - Drag-drop reordering support for selected files
  - Backward compatibility with single-tab code
  - Dynamic settings import to avoid circular dependencies
  - Smart tab numbering that finds highest existing number

### fileSystemStore.ts

Manages the file tree representation and UI preferences:
- **File Tree State**: Complete project structure with metadata
- **Configuration**: Merged application and project settings
- **UI Preferences**: Smart preview, file tree inclusion, format type, project info inclusion
- **Analysis Tracking**: Background graph analysis progress indicators
- **Key Features**:
  - Toggle methods for all boolean settings
  - Effective config merging from multiple sources
  - Clean state reset functionality
  - Default XML format support with Markdown fallback

### contextStore.ts

Intelligent context building with relevance scoring:
- **Neighbor Discovery**: Fetches files related to current selection and task
- **State Management**: Selected files, neighboring files, heuristic seeds, prompt neighbors
- **Request Tracking**: Prevents duplicate requests with ID and key-based caching
- **IPC Integration**: Heavy communication with RelevanceEngineService
- **Key Features**:
  - Race condition handling with request IDs
  - Smart caching to reduce IPC calls
  - Debug logging for troubleshooting
  - Stack trace capture for undefined task descriptions

### applyChangesStore.ts

File operation management for AI-generated changes:
- **Operation Types**: CREATE, UPDATE_FULL, UPDATE_DIFF, DELETE
- **Mode Support**: Both 'ai' and 'git' modes with different behaviors
- **Diff Matching**: Strict and fuzzy modes for flexibility
- **State Structure**: Active operations array with accepted/rejected status
- **Key Features**:
  - Path normalization for cross-platform support
  - Post-operation callbacks for UI updates
  - Different rejection behavior for Git mode (file reversion)
  - Validation after UPDATE_DIFF operations
  - Error handling with graceful fallbacks

### settingsStore.ts

Centralized settings management with loading states:
- **Dual Settings**: Separate project and application settings
- **Loading States**: Track loading and error states independently
- **Path Tracking**: Prevents redundant loads of same settings
- **Side Effects**: Triggers ignore rules reload on save
- **Key Features**:
  - Graceful fallback to defaults
  - Error state management
  - Integration with FileService for reloads
  - Last opened project path tracking

### promptStore.ts & taskStore.ts

Template management with variant support (parallel implementations):
- **Template Storage**: Arrays of PromptData/TaskData with variants
- **Active Variants**: Persistent mapping of active selections
- **Persistence**: Uses Zustand persist middleware with local storage
- **Sorting**: Auto-sorts by order then alphabetically
- **Key Features**:
  - Smart fallback chain for variant selection
  - Local storage persistence for selections only
  - Identical pattern for both stores
  - Default variant resolution logic

### commandStore.ts

Clipboard monitoring and validation:
- **Real-time Parsing**: Validates clipboard content for commands
- **State Tracking**: Raw content, parsed commands, and validation status
- **Multiple Commands**: Support for single and multiple command scenarios
- **Key Features**:
  - Backward compatibility handling
  - Quick validation boolean for UI decisions
  - Integration with command parser

### logStore.ts

Application-wide logging system:
- **Interactive Logs**: Support for clickable entries with callbacks
- **Auto-increment IDs**: Ensures unique log entries
- **Timestamp Addition**: Automatic locale-based timestamping
- **Flexible API**: Accepts string or structured log entries
- **Key Features**:
  - Used extensively by other stores
  - Enables debugging navigation
  - Simple but powerful API

### cliStore.ts

Terminal session persistence:
- **Session Mapping**: Directory to session ID map structure
- **State Management**: Session creation, retrieval, and removal
- **Component Survival**: Maintains sessions across UI remounts
- **Key Features**:
  - Enables terminal reattachment
  - Simple Map-based implementation
  - Project-specific session isolation

## State Management Patterns

1. **Store Independence**: Each store manages its own domain with minimal coupling
2. **Type Safety**: Full TypeScript typing throughout with strict mode
3. **Derived State**: Computed values and getters for performance
4. **Async Handling**: Proper async/await patterns for IPC operations
5. **Error States**: Consistent error handling with type narrowing
6. **Persistence Strategy**: Selective persistence based on need (settings, active variants)

## Integration Patterns

### IPC Communication
Many stores communicate with main process services:
```typescript
const result = await window.electronBridge.context.recalculate()
const settings = await window.settingsService.getProjectSettings()
```

### Inter-store Communication
Stores can access other stores when needed:
```typescript
const { addLog } = useLogStore.getState()
const { applicationSettings } = useSettingsStore.getState()
```

### UI Updates
Components subscribe to store changes:
```typescript
const { tabs, activeTabIndex } = useWorkbenchStore()
const smartPreviewEnabled = useFileSystemStore(state => state.smartPreviewEnabled)
```

## Performance Considerations

- **Selective Subscriptions**: Components can subscribe to specific slices
- **Request Deduplication**: Prevents redundant expensive operations
- **Lazy Loading**: Settings loaded on demand
- **Atomic Updates**: Batch updates when possible
- **Memory Management**: Proper cleanup of session data

## Testing

The directory includes comprehensive test coverage:
- **workbenchStore.test.ts**: Validates tab management, file selection, and folder operations
- **Mock Utilities**: File selection utilities mocked for isolation
- **Fake Timers**: Prevents setTimeout memory leaks in tests
- **State Reset**: Clean slate between test cases

## Architectural Benefits

1. **Centralized State**: Single source of truth for each domain
2. **Predictable Updates**: Clear action methods with immutable updates
3. **DevTools Support**: Time-travel debugging capabilities
4. **Type Safety**: Full TypeScript support with inference
5. **Performance**: Minimal re-renders through selective subscriptions
6. **Maintainability**: Clear domain boundaries and responsibilities

This store architecture provides a robust foundation for complex state management while maintaining simplicity and performance. The consistent patterns across stores make it easy to understand and extend the application state management.
