# Directory: src

## Overview

The `src/` directory contains the entire renderer process implementation for Athanor, a desktop application for AI-assisted development workflows. Built with React 19 and TypeScript, this directory implements a sophisticated UI that enables developers to create context-rich prompts from their codebase and apply AI-generated changes safely.

The architecture follows Electron's security best practices by strictly separating renderer and main process concerns, with all file system operations routed through secure IPC channels. State management is handled by Zustand stores, providing a clean, performant alternative to Redux.

## Key Components

### App.tsx

The minimal React application root that delegates all functionality to AthanorApp. This separation allows for easy testing and potential wrapper injection while keeping the entry point simple and focused.

### index.tsx

The renderer process entry point that mounts the React application using React 18's concurrent features. Includes strict mode for development-time checks and proper error handling for missing DOM elements.

### index.css

Global styles importing Tailwind CSS and defining application-wide CSS variables and base styles. Includes:
- Dark mode configuration with proper color schemes
- Custom scrollbar styling for consistent UI
- Floating label tooltips with hover animations
- Context field and dropdown styling
- File explorer hover effects and heuristic seed highlighting
- Syntax highlighter integration for code viewing

## Architecture Layers

### Component Layer (`components/`)

The UI is organized into several major components:

- **AthanorApp**: Root component managing application lifecycle, theme, and project initialization
- **MainLayout**: Three-panel layout with resizable file explorer (left), content area (right), and logs (bottom)
- **ActionPanel**: Primary workflow interface for task description, file selection, and prompt generation
- **FileExplorer**: Recursive tree component with selection states, context menus, and relevance visualization
- **ReviewPanel**: Sophisticated diff viewer for reviewing and applying AI-generated changes
- **SettingsPanel**: Comprehensive settings management for project, application, and API keys
- **FileViewerPanel**: Syntax-highlighted code viewer with copy/replace functionality
- **CliPanel**: Integrated terminal using xterm.js and node-pty for shell access

### State Management (`stores/`)

Zustand stores provide centralized state management:

- **workbenchStore**: Multi-tab task management with per-tab file selections and outputs
- **fileSystemStore**: File tree representation and UI preferences
- **contextStore**: Intelligent context building with relevance-scored neighboring files
- **applyChangesStore**: File operation management for AI-generated changes
- **settingsStore**: Project and application settings with loading states
- **promptStore/taskStore**: Template management with variant support
- **commandStore**: Clipboard monitoring for AI commands
- **logStore**: Application-wide logging with interactive entries
- **cliStore**: Terminal session persistence

### Service Layer (`services/`)

Services handle business logic and external integrations:

- **fileSystemService**: Builds file trees with proper ignore pattern support
- **promptService**: Loads XML templates from multiple sources with priority merging
- **fileIgnoreService**: Manages .athignore files with .gitignore integration
- **athanorPresetService**: Validates AI model configurations against available providers

### Action Layer (`actions/`)

Actions bridge UI events to business operations:

- **buildTaskAction**: Orchestrates prompt generation from templates
- **ManualCopyAction**: Clipboard operations with token counting
- **ApplyAiOutputAction**: Processes AI commands with intelligent aggregation

### Command System (`commands/`)

XML-based command parsing and execution:

- **Command Types**: SELECT, TASK, APPLY_CHANGES, AGENT_TASK
- **Robust Parsing**: Handles escaped characters, CDATA blocks, platform differences
- **Safe Execution**: Validation before action with detailed user feedback

### Utilities (`utils/`)

Foundation utilities powering core features:

- **buildPrompt**: Dynamic prompt assembly with variable substitution
- **codebaseDocumentation**: Structured file content generation with smart previews
- **fileOperations**: Diff-based file updates with fuzzy matching support
- **tokenCount**: Accurate token counting using OpenAI's tokenizer
- **fileTree**: Core data structures and tree traversal algorithms

### Custom Hooks (`hooks/`)

React hooks encapsulating complex logic:

- **useFileSystemLifecycle**: Manages file system initialization and updates
  - Handles project loading with .athignore detection
  - Manages file watchers with debounced updates
  - Integrates with settings for configuration changes
  - Provides centralized refresh mechanism
- **usePanelResize**: Handles resizable panel interactions
  - Manages horizontal panel width with mouse tracking
  - Provides configurable min/max constraints
- **useLogPanelResize**: Vertical resize for bottom log panel
  - Similar to usePanelResize but for vertical resizing
- **useFileDrop**: Enables drag-and-drop file selection
  - Calculates drop position in text areas
  - Preserves cursor position after drops
  - Integrates with logging for feedback
- **useDarkMode**: Theme management with persistence
  - Respects user's 'Auto', 'Light', or 'Dark' preference
  - Listens to system theme changes in Auto mode
  - Uses native theme bridge for OS integration

### Configuration (`config/`)

Static configuration files defining application defaults:

- **athanorModelPresets.json**: Pre-configured AI model settings
  - Anthropic Claude models (Sonnet 4, Opus 4, 3.7, 3.5)
  - Google Gemini models (2.5 Pro/Flash, 2.0 Flash)
  - OpenAI models (o4-mini, GPT-4.1 series)
  - Mistral models (Codestral, Devstral)
  - Each preset includes temperature settings and provider-specific configs

### Type Definitions (`types/`)

TypeScript interfaces and type definitions:

- **global.d.ts**: Window API extensions and core types
  - Electron bridge interfaces for IPC communication
  - File system, LLM service, settings service APIs
  - Shell/terminal integration types
  - Project and application settings interfaces
  - Workbench state and task tab definitions
- **athanorPresets.ts**: Model preset type definitions
  - Interfaces for AI model configurations
  - Links to genai-lite provider types
- **promptTypes.ts**: Prompt template system types
  - PromptData with variants and metadata
  - Active variant tracking
  - Store interface for prompt management
- **taskTypes.ts**: Task template system types
  - Similar to prompts but for task presets
  - Includes 'requires' field for conditional activation

## Internal Dependencies

The architecture follows clear dependency flows:

1. **Components** depend on stores for state and services for operations
2. **Stores** use services and utilities, communicate via IPC
3. **Services** depend on utilities and window APIs
4. **Actions** orchestrate between stores, services, and utilities
5. **Commands** update stores and trigger UI changes
6. **Utilities** are foundational with minimal dependencies

## External Dependencies

Key external libraries integrated throughout:

- **React 19**: UI framework with concurrent features
- **Zustand**: Lightweight state management
- **react-syntax-highlighter**: Code viewing with language support
- **xterm.js**: Terminal emulation in the browser
- **js-tiktoken**: OpenAI-compatible token counting
- **diff-match-patch**: Fuzzy text matching for updates
- **Material-UI**: Component library for consistent UI

## Security Architecture

All file operations follow secure patterns:

1. Renderer requests operations via typed IPC methods
2. Preload script validates and forwards to main process
3. Main process performs operations with full Node.js access
4. Results returned through secure bridge

This ensures the renderer never has direct file system access, following Electron security best practices.

## Data Flow

A typical user workflow follows this pattern:

1. User selects files in FileExplorer → updates workbenchStore
2. User enters task description → stored in active tab
3. Context builder fetches relevant files → updates contextStore
4. User clicks generate → buildTaskAction assembles prompt
5. Prompt copied or sent to AI → response processed by commands
6. Apply changes parsed → operations shown in ReviewPanel
7. User reviews and applies → changes written via IPC

## Performance Optimizations

- File tree uses ID-based lookups for O(1) access
- Relevance scoring cached with request deduplication
- Token counting uses singleton encoder
- Virtual scrolling planned for large file trees
- Debounced file watching prevents excessive updates

This architecture provides a robust, secure, and performant foundation for AI-assisted development workflows.
